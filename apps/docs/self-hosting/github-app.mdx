---
title: GitHub App
description: Publish commit statuses as a GitHub App instead of with a personal access token.
---

OVR posts a commit status to GitHub for each build. By default each project stores an access token for this, which belongs to whoever created it and stops working when they leave or the token expires. A GitHub App avoids that: the statuses come from the App, and OVR mints short-lived tokens for it as needed.

You create one App for your OVR deployment, install it on the repositories you want statuses on, and then switch each project to use it.

## Create the App

1. In GitHub, open **Settings → Developer settings → GitHub Apps → New GitHub App**. To own the App with an organization, start from the organization's settings instead.
2. Give it a name, such as `OVR`, and set the **Homepage URL** to your OVR address.
3. Under **Webhook**, clear **Active**. OVR doesn't receive webhooks.
4. Under **Repository permissions**, set:
   - **Commit statuses**: Read and write
   - **Metadata**: Read-only (GitHub requires this for every App)

   Leave every other permission at **No access**.
5. Under **Where can this GitHub App be installed?**, choose **Only on this account** unless you need it elsewhere.
6. Click **Create GitHub App**.

On the App's settings page, note the **App ID**. Then, under **Private keys**, click **Generate a private key**. GitHub downloads a `.pem` file, which is the only copy of the key.

## Install the App

From the App's settings page, open **Install App** and install it on the account or organization that owns your repositories. Choose **All repositories**, or **Only select repositories** and pick the ones OVR builds.

To add repositories later, open the installation's **Configure** page from the account's or organization's **Settings → GitHub Apps**.

## Configure OVR

Give the web app and the worker the App ID, and mount the private key into both as a file:

| Variable | Description |
| --- | --- |
| `OVR_GITHUB_APP_ID` | The App ID. |
| `OVR_GITHUB_APP_PRIVATE_KEY_FILE` | Path to the `.pem` file inside the container. |

Set both or neither. The web app and worker refuse to start if only one is set, or the file can't be read or doesn't hold an RSA private key, and the error names the variable or file at fault. The key is read from the file once at startup. It is never put in the environment or stored in the database.

### Docker Compose

Mount the key as a [Compose secret](https://docs.docker.com/compose/how-tos/use-secrets/). Put the `.pem` file next to `docker-compose.yml`, then create `docker-compose.override.yml` beside them. Compose merges the override file into `docker-compose.yml` automatically:

```yaml docker-compose.override.yml
secrets:
  github_app_private_key:
    file: ./github-app.private-key.pem

services:
  web:
    secrets: [github_app_private_key]
    environment:
      OVR_GITHUB_APP_ID: "123456"
      OVR_GITHUB_APP_PRIVATE_KEY_FILE: /run/secrets/github_app_private_key
  worker:
    secrets: [github_app_private_key]
    environment:
      OVR_GITHUB_APP_ID: "123456"
      OVR_GITHUB_APP_PRIVATE_KEY_FILE: /run/secrets/github_app_private_key
```

Compose mounts the file with the permissions it has on the host, and the containers run as user `1001`, so make it readable by that user:

```sh
sudo chown 1001 github-app.private-key.pem
chmod 400 github-app.private-key.pem
```

Then run `docker compose up -d` to restart the web app and worker with it.

### Helm

Set the App ID and the key, and the chart mounts the key into the web and worker pods:

```yaml
githubApp:
  appId: 123456
  privateKey: |
    -----BEGIN RSA PRIVATE KEY-----
    MIIE...
    -----END RSA PRIVATE KEY-----
```

With `existingSecret`, set only `githubApp.appId` and add the key to your Secret under `github-app-private-key.pem`. For example, to create the Secret by hand:

```sh
kubectl create secret generic ovr-secrets \
  --from-literal=DATABASE_URL=... \
  --from-file=github-app-private-key.pem=github-app.private-key.pem
```

The chart reads each of its environment variables from the Secret by name, so the key is only mounted as a file and never reaches the environment.

### Rotating the key

Generate a new key on the App's settings page, replace the file or the key in your Secret, and restart the web app and worker. With `githubApp.privateKey`, `helm upgrade` restarts them for you. Then delete the old key from the App's settings page.

### Upgrading from `OVR_GITHUB_APP_PRIVATE_KEY`

Earlier versions read the key from `OVR_GITHUB_APP_PRIVATE_KEY`. That variable is no longer read. If you set it, mount the key as a file as described above and set `OVR_GITHUB_APP_PRIVATE_KEY_FILE` instead:

- **Docker Compose**: move `OVR_GITHUB_APP_ID` from `.env` into `docker-compose.override.yml`, save the key as a `.pem` file (the one GitHub downloaded, or a newly generated one), and delete both variables from `.env`.
- **Helm with `githubApp.privateKey`**: no change is needed, unless you put the key on one line with `\n` escapes. Write it as a multi-line string instead, as shown above.
- **Helm with `existingSecret`**: in your Secret, rename `OVR_GITHUB_APP_PRIVATE_KEY` to `github-app-private-key.pem` and give it the key with real line breaks, remove `OVR_GITHUB_APP_ID`, and set `githubApp.appId` instead.

Until you do, either the web app and worker refuse to start because `OVR_GITHUB_APP_ID` is set without `OVR_GITHUB_APP_PRIVATE_KEY_FILE`, or projects set to **github app** fail to publish statuses with "GitHub App authentication is not configured on this deployment".

## Switch a project to the App

1. Open the project's **settings** page.
2. Under **git integration**, set **authentication** to **github app**. The choice only appears once the App is configured.
3. Enter the repository as `owner/repo` and click **save**.
4. Click **test connection**. It checks that the App is installed on the repository and has permission to write commit statuses.

Switching a project to the App deletes its stored token. To switch back, choose **access token** and enter a new one.

## How tokens are handled

To publish a status, OVR signs a short JWT with the App's private key, looks up the App's installation for the repository, and exchanges the JWT for an installation token. Installation tokens expire after an hour.

Each web and worker process caches its installation tokens in memory, one per installation, and replaces a token five minutes before it expires. Concurrent publishes share a single refresh. If GitHub rejects a cached token, OVR fetches a new one and retries the status once. Nothing about these tokens is written to the database, so a restarted process simply mints new ones.

## Troubleshooting

**the GitHub App is not installed on owner/repo**: install the App on that repository, or add the repository to its installation. Check the repository name in the project's settings.

**the GitHub App cannot write commit statuses**: give the App the **Commit statuses: Read and write** permission. After changing an App's permissions, the account or organization that installed it has to approve the change on the installation before it takes effect.

**GitHub rejected the App's credentials**: the App ID and the key in `OVR_GITHUB_APP_PRIVATE_KEY_FILE` don't match, or the key was revoked. Check both, and generate a new key if needed.

Publishing failures are also recorded in the `ovr_git_status_publications_total` metric with `outcome="error"`, and logged by the worker. See [Metrics](/self-hosting/metrics).

GitHub Enterprise Server isn't supported yet.
